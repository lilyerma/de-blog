    Когда нужны коррелированные подзапросы

    Коррелированные подзапросы долгое время считались антипаттерном из-за потенциально низкой производительности ($O(N \times M)$), однако в современном SQL есть три ключевых сценария, где их использование абсолютно оправдано, красиво и часто эффективнее альтернатив.

    1. Проверка существования связей (EXISTS / NOT EXISTS)

    Это самый частый и правильный сценарий использования коррелированных подзапросов в продуктовой разработке и ETL-процессах.

    Когда тебе нужно проверить, есть ли у объекта связанные записи в другой таблице (или наоборот — найти сирот), коррелированный EXISTS работает быстрее, чем LEFT JOIN ... WHERE id IS NULL или WHERE id IN (...).

    SQL

    -- Найти клиентов, которые совершили хотя бы одну покупку за последний месяц
SELECT c.customer_id, c.name
FROM customers c
WHERE EXISTS (
    SELECT 1 
    FROM orders o 
    WHERE o.customer_id = c.customer_id -- <-- Корреляция
      AND o.order_date >= NOW() - INTERVAL '30 days'
);

    Почему это отлично работает:

    • Короткое замыкание (Short-circuiting): Оптимизатор СУБД останавливает поиск в таблице orders сразу же, как только находит первое совпадение для клиента. Ему не нужно сканировать и агрегировать все покупки клиента.

    • Нет дублирования строк: В отличие от JOIN, который размножил бы клиента c на количество его заказов (потребовался бы DISTINCT), EXISTS всегда возвращает ровно одну строку для каждого клиента.

    2. Латеральные соединения (LATERAL JOIN)

    LATERAL в PostgreSQL — это суперсила коррелированных подзапросов. Он позволяет подзапросу в секции FROM обращаться к колонкам из предшествующих таблиц.

    Это стандарт индустрии для задач класса Top-N per Group (например: «получить по 3 самых дорогих товара для каждого производителя»).

    SQL

    SELECT m.maker, p.model, p.price
FROM (SELECT DISTINCT maker FROM Product) m
CROSS JOIN LATERAL (
    SELECT model, price
    FROM Product p
    WHERE p.maker = m.maker -- <-- Корреляция с внешней таблицей m
    ORDER BY price DESC
    LIMIT 3
) p;

    Почему это отлично работает:

    Если по полю (maker, price) есть индекс, PostgreSQL выполнит этот запрос за считанные миллисекунды (Index Scan по $3$ строки для каждого производителя). Оконная функция ROW_NUMBER() в этом случае сканировала бы всю таблицу Product целиком.

    3. Точечные рассуждения в вычисляемых колонках (SELECT)

    Когда нужно обогатить выборку однократно вычисляемым значением из связанной таблицы, а делать тяжелый JOIN со всей таблицей не хочется или это раздует число строк.

    SQL

    SELECT 
    o.order_id,
    o.order_date,
    -- Вычисляем дату предыдущего заказа этого же клиента
    (
        SELECT MAX(prev.order_date)
        FROM orders prev
        WHERE prev.customer_id = o.customer_id -- <-- Корреляция
          AND prev.order_date < o.order_date
    ) AS prev_order_date
FROM orders o;

    Почему это оправдано:

    Если нам нужно достать ровно одно точечное скалярное значение, сканируя небольшую часть индекса, такой подзапрос читается очень наглядно и не требует группировки внешнего запроса.

    Чек-лист: Когда стоит использовать коррелированный запрос?

    1. ✅ Ты используешь операторы EXISTS или NOT EXISTS.

    2. ✅ Тебе нужно решить задачу Top-N в группе с помощью LATERAL JOIN при наличии подходящих индексов.

    3. ✅ Вложенный подзапрос использует Индекс (Index Scan) по полю корреляции. В этом случае $N$ выборок по индексу работают мгновенно.

    4. ❌ НЕ стоит использовать: Если подзапрос заставляет СУБД делать полный сканирующий проход по таблице (Seq Scan) для каждой строки внешнего запроса. В таких случаях лучше переписать на JOIN или оконные функции.
