    Как формулировать бизнес правила

    Справочная информация (RuleSpeak):

    • Хорошее бизнес-правило содержит глагол ДОЛЖНО (или не должно, может), а также наречия ВСЕГДА, НИКОГДА, ТОЛЬКО.

    • Оно обязательно включает в себя субъект (кто/что) и объект (кого/что).

    • Чем меньше правил, тем лучше, но они должны однозначно определять поведение системы в различных ситуациях.

    Категория правила / Тип Шаблон формулировки Пример
    1.0 Правила, обозначающие требования … должен(-а) …
    1.1.1 Безусловное требование … должен(-а) … Диск должен иметь тип
    ВМ должна иметь статус
    Письмо о прогнозе превышения бюджета должно отправляться один раз в день
    1.1.2 Требование по условию (с «если») … должен(-а) …, если Пользователь должен видеть страницу План, если есть активная подписка
    Пользователь должен видеть новый тип диска в Таблице ресурсов, если подключил новый тип диска в своем облаке.
    1.1.3 Требование по условию (без «если») … должен(-а) … В 00:00 UTC сумма затрат за день должна быть сохранена одним числом (финализирована)
    Пользователь должен быть в роли Администратор, чтобы видеть Отчеты
    1.2 Расчетные правила … считается, как … Общая сумма оптимизации считается, как сумма оптимизаций по каждому подключению.
    Сумма оптимизации по подключению считается, как сумма только известных значений оптимизации всех типов в этом подключении.
    1.3 Правила вывода состояний … считается…, когда… Бюджет считается превышен, когда сумма затрат превышает установленный лимит
    Инфраструктура считается неоптимизированной, когда число рекомендаций больше нуля
    Диск считается забытым, когда он не был прикреплен к ВМ больше 14 дней
    2.0 Правила, обозначающие запреты
    2.1 Безусловный запрет … не должно … Имена облаков в одном кастомере не должны совпадать
    2.2 Запрет по условию (с «если») … не должно …, если Система не должна создавать заявку на увеличение подписки, если запрошенный лимит больше размера доступных свободных ресурсов
    2.3 Запрет по условию (без «если») … не должно … Прототипы не должны быть видны пользователю
    3.0 Правила условного разрешения
    3.1 Разрешение (с «только если») … может …, только если Пользователь может увидеть прототип, только если менеджер включил его в менеджерской панели
    3.2 Разрешение (без «только если») … может … только Пользователь в роли Владелец может видеть только свои подписки
    4.0 Утверждения о разрешениях
    4.1 Безусловное разрешение … может … Пользователь может видеть главный дашборд
    4.2 Разрешение с условиями (без «если») … может … Менеджер может включить отображение прототипа в кастомере
    5.0 Утверждения об отсутствии требований
    5.1 Безусловное отсутствие требования … может не … Пользователь может не вносить цены на ресурсы подключения
    5.2 Отсутствие требования с условием (с «если») … может не …, если Глобальный администратор может не делать выбор облака или хоста в заявке, если Владелец указал облако или хост в заявке.
    5.3 Отсутствие требования по условию (без «если») … может не … Глобальный администратор может не согласовывать заявки
